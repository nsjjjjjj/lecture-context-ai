# STT PhraseSet 파일럿 실험 기록

작성일: 2026-08-09

## 1. 이 문서의 목적

현재까지 실제 Google Speech-to-Text V2로 수행한 고정음원 비교 결과와 그 한계를 보존한다. 이 실험은 연결과 표기 변화가 발생하는지 확인한 **파일럿 스모크 테스트**이며, 아직 논문에 전문용어 정확도 수치로 인용할 수 있는 정식 실험은 아니다.

## 2. 실험 자료

- 녹음 ID: `6d9c7e31-9df8-454d-b6fa-8a7423773163`
- 음원: `test-fixtures/stt/audio/20260809001249-6d9c7e31-9df8-454d-b6fa-8a7423773163.wav`
- 길이: 106.435초
- 형식: 16 kHz, mono, 16-bit PCM WAV
- 환경: `speaker-a`, quiet
- 비교 결과: `test-fixtures/stt/results/comparison-6d9c7e31-9df8-454d-b6fa-8a7423773163.json`
- STT 조건: Google Speech-to-Text V2, `chirp_3`, `ko-KR`, `us`

음원과 결과 JSON은 개인정보 및 API 결과를 포함할 수 있어 Git과 Docker에서 제외된다. 이 문서는 원본 자격증명이나 개인정보를 기록하지 않는다.

## 3. 수행한 비교

같은 WAV를 실시간 속도로 두 번 재생했다.

1. PhraseSet 없이 인식
2. 고정 실험 문장의 영문 `targetTerms` 17개를 PhraseSet으로 제공해 인식

두 실행 모두 전체 음원을 처리했고 오류 없이 완료됐다.

| 조건 | 상태 | interim 수 | final 수 | 영문 targetTerms 정확 표기 |
|---|---|---:|---:|---:|
| PhraseSet 없음 | 완료 | 11 | 12 | 0개 |
| 영문 PhraseSet | 완료 | 12 | 12 | 1개 (`PhraseSet`) |

위의 `0개`, `1개`는 결과 문자열이 17개 영문 후보와 정확히 일치했는지만 센 값이다. 실제 발화 횟수를 분모로 계산한 전문용어 인식률이 아니다.

## 4. 대표 관찰

| 의도한 용어 | 관찰된 표기 | 현재 용어 연결 | 해석 |
|---|---|---|---|
| `RAG` | `레그` | 실패 | 발음에 가까운 한글은 생성했지만 영문 용어와 연결하지 못함 |
| `Transformer` | `트랜스포머` | 실패 | 한글 음역을 영문 표기와 다른 문자열로 취급함 |
| `Fine-tuning` | `파인 튜닝` | 실패 | 공백을 포함한 한글 음역을 canonical term과 연결하지 못함 |
| `PhraseSet` | 미적용 시 `프레이저스 셋` 등, 적용 시 `PhraseSet` | 적용 조건 일부 성공 | 영문 PhraseSet만으로도 특정 발화는 영문 표기로 바뀔 수 있음 |
| `LLM` | `LLM` | 평가 대상에서 누락 | 실제 발화에는 있었지만 기준 `targetTerms`에는 `Large Language Model`만 있어 현재 자동 집계가 세지 못함 |
| `PDF.js` | 미적용 시 `PDF. 자바스크립트`, 적용 시 `PDF.js` | 평가 대상에서 누락 | 실제 변화가 있어도 targetTerms 밖의 용어는 현재 비교표에 나타나지 않음 |

핵심적으로, STT가 소리를 완전히 놓친 경우와 한글 음역으로 받아 적었지만 애플리케이션이 용어로 연결하지 못한 경우가 현재 집계에서 모두 `미인식`으로 보인다. 두 실패 유형을 다음 평가에서는 분리해야 한다.

## 5. 정확도 결과로 사용할 수 없는 이유

- 녹음할 때 화면의 고정 기준 문장을 그대로 읽지 않고 별도의 프로젝트 소개 대본을 읽었다.
- 기준 `targetTerms` 17개 중 실제로 발화하지 않은 후보가 포함되어 있다.
- 반대로 `LLM`, `PDF.js`처럼 실제로 발화했지만 기준 목록과 맞지 않거나 목록에 없는 용어가 있다.
- 용어별 실제 발화 횟수와 정확한 시작·종료 위치가 표시된 정답 대본이 없다.
- 한글 음역을 부분 성공으로 볼지, 영문 표기 실패로 볼지 평가 규칙이 아직 고정되지 않았다.

따라서 `0/17 → 1/17`을 전문용어 정확도 향상으로 발표하거나 논문에 쓰면 안 된다. 현재 근거로 말할 수 있는 것은 다음 두 가지다.

1. 같은 저장 음원을 PhraseSet 없음/적용 조건으로 재현 가능하게 Google STT에 전송하는 경로가 정상 동작한다.
2. 영문 PhraseSet만으로 일부 표기는 개선됐지만 한국어식 영어 발음은 한글 음역으로 남아 용어 연결에 실패하는 사례가 관찰됐다.

## 6. 구현 반영 상태

2026-08-09에 다음 범위를 구현했다.

- `GlossaryTerm.spokenAliases`와 Gemini 구조화 출력 필드
- 영문 원어가 있는 용어에 한해 용어당 최대 6개·2~40자·완성형 한글 중심으로 검증하되, 코드에서 검토된 용어-발음 쌍만 채택하고 일반 단어·용어 간 충돌을 차단
- `RAG`, `LLM`, `Transformer`, `Fine-tuning`, `PhraseSet` 등 관찰된 기술용어의 보수적인 알려진 발음 보완
- 검증된 별칭을 포함할 수 있는 최대 50개 PhraseSet
- 브라우저 용어집 v3, 기존 v1의 빈 별칭 유지 이전, v2의 미검토 별칭 제거 이전
- 임시 자막 원문 유지
- 확정 자막에서 원문 `rawText`와 정정 위치를 보존한 `레그 → RAG` canonical 정정
- 화면과 결과 자막의 눈에 보이는 `자동 정정` 표지, 포커스/호버 원문 설명
- 별칭으로 연결된 canonical 용어의 반복 설명 카드 생성
- 고정음원 비교 결과에 정정 표시문과 STT 원문을 함께 남기는 결과 형식 v2

이 구현은 문자열 전체를 무조건 바꾸지 않는다. 정규화된 원문 위치를 기준으로 가장 긴 후보를 왼쪽부터 선택하며, 검토되지 않은 임의 별칭은 API 입력에 있어도 무시한다. `레그`는 모호한 별칭으로 분류해 `레그는`은 RAG 후보로 보지만 `레그레이즈` 안의 `레그`와 `레그 프레스`는 바꾸지 않는다. 그래도 의미 문맥을 완전히 판별하는 모델은 아니므로 화면에서 원문과 정정 사실을 숨기지 않는다.

## 7. 다음 실험 판단

가장 먼저 할 일은 결과 화면을 꾸미는 것이 아니라 **발음 별칭을 공식 데이터로 지원하는 것**이다. 현재 실패 사례가 제품의 핵심 기능인 용어 설명 연결을 직접 막고 있고, 해커톤 연구 주제로도 명확한 비교 조건을 만들 수 있기 때문이다.

### 완료: 발음 별칭 데이터 모델

용어에 다음 필드를 추가한다.

```json
{
  "term": "RAG",
  "english": "Retrieval-Augmented Generation",
  "spokenAliases": ["래그", "레그", "알에이지"]
}
```

- Gemini 출력, 서버 검증 타입, 데모 데이터, 브라우저 저장 형식을 함께 갱신한다.
- v1 저장 용어집은 별칭이 없는 데이터로, v2는 검토된 별칭만 남기는 데이터로 안전하게 이전한다.
- 자동 생성된 별칭은 후보로 취급하고 검토 목록 일치·중복·길이·문자 제한을 검증한다.
- 별칭 직접 수정 UI는 아직 없으며, 실제 오정정 결과를 본 뒤 필요성을 판단한다.

### 완료: STT 힌트와 화면 매칭에 동시에 사용

- PhraseSet에는 영문 canonical 표기와 검증된 한글 발음 별칭을 함께 전달한다.
- 자막에 `레그`가 나오면 canonical 용어 `RAG`로 연결해 같은 설명 카드를 생성한다.
- 임시 자막은 원문을 유지한다. 확정 자막은 `RAG`로 표시하되 원본 `레그`를 프로토콜·상태에 보존하고 `자동 정정: 레그 → RAG`를 화면에서 확인하게 한다.
- 자동 정정과 PhraseSet에 쓰는 별칭은 코드에서 검토한 용어-발음 쌍으로 제한하고, 모호한 `레그`에는 `레그 프레스` 오정정을 막는 문맥 경계를 둔다. 새 별칭은 실험 결과를 검수한 뒤 목록과 회귀 테스트에 함께 추가한다.

### 다음: 동일 음원 A/B/C 비교

같은 음원으로 다음 세 조건을 비교한다.

| 조건 | PhraseSet | 화면 용어 매칭 |
|---|---|---|
| A | 없음 | canonical 표기만 |
| B | 영문 표기만 | canonical 표기만 |
| C | 영문 + 한글 발음 별칭 | canonical + 발음 별칭 |

기존 106초 음원은 구현 스모크 테스트에 그대로 재사용할 수 있다. 다만 정식 수치를 만들 때는 다음 중 하나가 필요하다.

- 현재 음원의 실제 발화를 그대로 옮긴 정답 대본과 용어 출현 목록을 작성해 검수하거나
- 화면의 고정 기준 문장을 그대로 읽은 새 음원을 한 번 녹음한다.

### 후속: 평가 규칙 고정

용어 출현 한 건마다 다음을 구분한다.

- 영문 canonical 표기로 정확히 인식
- 한글 음역으로 인식하고 canonical 용어 연결 성공
- 잘못된 단어로 인식하거나 용어 연결 실패
- 말하지 않은 용어를 PhraseSet 때문에 삽입한 오탐

제품 관점의 핵심 지표는 `설명 카드까지 올바르게 연결된 출현 수 / 실제 용어 발화 수`로 두고, ASR 자체의 영문 표기 정확도는 별도 지표로 보고한다.

### 후속: 결과 자동화와 UI

위 규칙이 정해진 다음 비교 실행기가 A/B/C 결과, 용어별 성공 여부, 오탐을 JSON으로 저장하게 한다. 마지막에 개발 화면에 최신 비교 결과 카드와 표·그래프를 추가하면 논문과 발표 자료로 바로 활용할 수 있다.

## 8. 권장 실행 순서

1. 기존 음원으로 A/B/C 연결 스모크 테스트
2. 현재 음원의 정답 대본을 검수하거나 기준 문장 음원을 한 번 재녹음
3. 출현 단위 전문용어 연결률·자동 정정 성공률·오탐 자동 집계
4. 결과 조회 UI와 논문용 표·그래프 생성
5. 실제 오정정 결과에 따라 별칭 검수·수정 UI 결정
6. 소음 환경 음원, 10분 이상 스트림, Cloud Run 환경으로 검증 확대

이 순서라면 제품 문제 해결과 논문용 연구 기여가 같은 구현에서 나온다. 현재 제품 경로의 완료 기준인 `레그`, `트랜스포머`, `파인 튜닝`의 canonical 정정·원문 표시·설명 카드 연결은 구현됐다. 다음 실험 완료 기준은 같은 음원의 A/B/C 결과에서 이 차이와 오정정 여부를 재현하고 정답 대본 기준 수치로 분리해 보고하는 것이다.
