# 강연맥락 AI 논문·발표 구성안

## 1. 이 프로젝트를 한 문장으로 정의하기

> 강연 전에 PDF에서 검증된 전문용어 사전을 만들고, 같은 사전을 실시간 음성인식 보정과 청중용 쉬운 설명·관련 페이지 연결에 동시에 사용하는 강연 이해 지원 시스템이다.

핵심은 단순히 “AI로 자막을 만든다”가 아니다. **강연 자료를 사전 맥락으로 활용해 전문용어 인식과 청중의 이해를 함께 지원한다**는 것이 이 프로젝트의 차별점이다.

### 추천 논문 제목

- **강연 자료 기반 전문용어 적응형 실시간 자막 및 맥락 정보 제공 시스템의 설계와 구현**
- **Lecture Context AI: PDF 기반 자동 용어집을 활용한 실시간 강연 이해 지원 시스템**
- 실험까지 완료한 뒤에만 사용: **PDF 기반 PhraseSet이 한국어 강연 전문용어 음성인식에 미치는 영향**

세 번째 제목은 정답 대본을 고정한 PhraseSet 적용 전후 실험 결과가 확보되었을 때만 쓴다. 실제 Google 자격증명과 106초 고정음원으로 A/B 연결 파일럿은 완료했지만, 녹음 대본과 평가 후보가 달라 아직 인식률 근거로 사용할 수 없다. 현재 관찰과 다음 A/B/C 설계는 [STT PhraseSet 파일럿 실험 기록](STT_PHRASESET_PILOT.md)에 정리되어 있다.

## 2. 논문의 중심 주장과 연구문제

### 중심 주장

일반적인 실시간 자막은 발화를 텍스트로 변환하지만, 낯선 전문용어의 정확한 표기와 의미 이해까지 보장하지 않는다. 강연자가 이미 준비한 PDF에는 해당 강연의 핵심 용어와 표기가 들어 있으므로, 이를 사전 분석해 만든 **문서 근거형 용어집**을 음성인식과 설명 UI에 재사용할 수 있다.

### 연구문제

- **RQ1.** 강연 PDF에서 음성인식에 유용한 전문용어를 자동 추출하면서 LLM의 근거 없는 표기를 얼마나 억제할 수 있는가?
- **RQ2.** PDF에서 검증한 용어를 PhraseSet으로 제공했을 때 일반 STT보다 전문용어 인식 정확도가 향상되는가?
- **RQ3.** 실시간 자막에 쉬운 설명과 관련 PDF 페이지를 함께 제공하면 사용자의 용어 이해와 사용 경험이 개선되는가?
- **RQ4.** 실시간성과 개인정보 보호라는 제약 아래 이 기능을 웹 기반 MVP로 안정적으로 구성할 수 있는가?

### 논문에서 제시할 기여

1. 페이지별 PDF 텍스트로부터 전문용어·영문 표기·쉬운 설명을 만드는 자동 용어집 파이프라인
2. LLM 후보를 PDF 원문과 재대조하고 정규화·중복 제거·상한 제한을 적용하는 근거 검증 절차
3. 하나의 검증된 용어집을 Google STT PhraseSet과 청중용 설명 카드에 함께 사용하는 이중 활용 구조
4. 실시간 자막, 전문용어 강조, 쉬운 설명, 관련 페이지를 한 화면에 배치한 접근성 중심 인터페이스
5. 원본 PDF와 음성을 애플리케이션 서버에 저장하지 않고, API 장애 시 보수적 휴리스틱과 데모 모드를 제공하는 MVP 운영 설계

## 3. 논문 전체 흐름

권장 형식은 **시스템 설계·구현 논문 + 정량·사용자 평가**다. 아직 실험이 끝나지 않았다면 결과를 만들어 쓰지 말고 “평가 설계”와 “현재 검증 범위”를 명확히 구분한다.

| 논문 절 | 쓸 내용 | 이 프로젝트에서 사용할 근거·그림 |
|---|---|---|
| 초록 | 문제, 제안 시스템, 핵심 구조, 실험 방법, 실제 측정 결과, 의의 순서로 5~7문장 | 마지막에 작성한다. 측정 전 수치 금지 |
| 1. 서론 | 강연 자막은 전문용어에서 취약하고, 정확히 표시돼도 비전공자는 의미를 모를 수 있다는 이중 문제 제시 | “자막 오류 → 용어 이해 실패” 사용자 장면, 기여 3~5개 |
| 2. 관련 연구 | ASR 문맥 적응, 교육용 자막과 확장 자막, LLM 환각과 근거 검증, 웹 접근성 | PhraseSet 공식 문서, contextual biasing 연구, 교육 자막 연구, WCAG |
| 3. 요구사항 및 설계 원칙 | 정확성, 이해 지원, 실시간성, 접근성, 개인정보, 장애 대응을 요구사항으로 정의 | 요구사항-구현 대응표 |
| 4. 시스템 구조 | PDF 분석 경로와 실시간 음성 경로를 분리해 설명 | README의 시스템 흐름도를 논문용 2단계 구조도로 다시 제작 |
| 5. 구현 | PDF.js, Gemini 구조화 출력, 서버 검증, PhraseSet, PCM/WebSocket/STT, React UI, 상태·입력 방어 | 주요 코드 위치와 핵심 자료구조, 단계별 의사코드 |
| 6. 평가 방법 | 용어 추출, STT 인식률, 지연, 사용자 이해·사용성 평가 설계 | 조건표, 데이터셋 표, 지표 수식, 실험 절차 |
| 7. 결과 | 실제 측정값과 통계만 제시하고 해석은 최소화 | 표 3개, 그래프 2~3개 |
| 8. 논의 | 왜 결과가 나왔는지, 실패 사례, 적용 가능 범위, 개인정보·윤리 | 오인식/오추출 사례, 사용자 의견, 비용·성능 절충 |
| 9. 한계 및 향후 연구 | OCR 미지원, 실제 문장 맥락 설명 미구현, 장시간 재연결 미구현, 외부 API 의존 | 현재 README/HANDOFF의 제한사항 |
| 10. 결론 | 문제-방법-검증 결과-의의를 한 문단씩 요약 | 새로운 주장이나 수치 추가 금지 |

## 4. “어떻게 만들었는가”를 설명하는 흐름

구현 설명은 사용한 기술 목록보다 **문제 → 판단 → 구현 → 안전장치** 순서로 쓴다.

### 4.1 강연 자료를 먼저 읽는 이유

- 전문용어, 약어, 제품명, 인명은 일반 언어보다 출현 빈도가 낮아 STT가 틀리기 쉽다.
- 반면 강연 PDF에는 강연자가 사용할 가능성이 높은 표기가 미리 존재한다.
- 따라서 실시간 음성이 들어오기 전에 PDF를 분석해 강연별 용어 사전을 준비한다.

### 4.2 PDF 분석 파이프라인

1. 브라우저의 PDF.js가 텍스트 PDF를 페이지별 문자열로 추출한다.
2. 페이지 번호를 포함한 텍스트를 Gemini에 보내 `term`, `english`, `easyExplanation` 구조의 JSON 후보를 생성한다.
3. 서버가 각 후보가 PDF 원문에 실제 존재하는지 다시 확인한다.
4. 유니코드 NFKC 정규화, 공백 정리, 중복 제거, 불필요한 일반어 제거를 적용한다.
5. 약어 여부, 등장 횟수, 첫 등장 페이지를 기준으로 정렬하고 최대 50개만 채택한다.
6. Gemini가 실패하거나 후보가 부족하면 문서에 실제 존재하는 약어·알려진 도메인 용어 중심의 보수적 휴리스틱으로 전환한다.

이 부분의 핵심 설명은 **“LLM은 후보 생성기이고, 최종 채택 권한은 원문 검증 로직에 있다”**이다. 단, 쉬운 설명 문장의 의미적 정확성까지 원문 대조로 검증하는 것은 아니므로 별도 평가 또는 강연자 검수가 필요하다.

### 4.3 음성인식 파이프라인

1. 브라우저가 마이크 권한을 얻고 입력 음성을 mono 16 kHz LINEAR16 PCM으로 변환한다.
2. 작은 오디오 청크를 WebSocket으로 Node.js 서버에 전송한다.
3. 검증된 용어와 PDF에 실제 존재하는 영문 확장 표기만 인라인 PhraseSet으로 구성한다.
4. Google Speech-to-Text V2의 `chirp_3`, `ko-KR`, 임시 결과 활성화 설정으로 스트리밍한다.
5. 서버가 `interim`과 `final` 자막 이벤트를 브라우저로 반환한다.
6. 확정 자막에서 용어를 찾고, 가장 관련 있는 용어의 쉬운 설명과 첫 등장 PDF 페이지를 연결한다.

Google 공식 문서는 PhraseSet 기반 모델 적응이 희귀어와 도메인 특화어를 더 자주 인식하도록 편향시키는 용도라고 설명한다. 따라서 “정확도가 반드시 오른다”가 아니라 **“향상을 의도한 입력을 제공하고, 효과는 동일 음원 A/B 실험으로 검증한다”**고 써야 한다.

### 4.4 사용자 화면

- 업로드: 텍스트 PDF, 10MB, 100페이지 제한을 사전에 안내한다.
- 준비: 추출 용어, 관련 페이지, PhraseSet 개수를 보여주어 시스템이 무엇을 준비했는지 투명하게 공개한다.
- 강연: 이전 자막, 현재 확정 자막, 임시 자막을 시각적으로 구분한다.
- 맥락 카드: 용어, 영문 표기, 쉬운 설명, 관련 페이지를 동시에 보여준다.
- 접근성: 자막 크기 3단계, 고대비, 전체화면, `aria-live`, 키보드 포커스, 모션 감소 설정을 제공한다.
- 결과: 확정 자막 수, 연결된 용어 수, 준비한 PhraseSet 수를 보고한다. 현재 화면의 “맥락 연결률”은 인식 정확도가 아니라 전체 용어집 중 이번 자막에 등장한 용어 비율이다.

### 4.5 안정성과 개인정보 처리

- API 요청은 Zod로 형식을 검증한다.
- WebSocket으로 다시 들어온 용어·PhraseSet도 서버에서 재검증하며, 용어집에 없는 임의 문구는 STT 힌트로 허용하지 않는다.
- live 모드에서는 빈 용어집을 데모 데이터로 대체하지 않아 시연 데이터와 실제 결과가 섞이지 않게 한다.
- 이전 세션의 늦은 비동기 이벤트가 새 세션을 덮어쓰지 않도록 세션 세대 번호로 차단한다.
- 애플리케이션은 원본 PDF와 음성 파일을 영구 저장하지 않는다. 다만 브라우저에서 추출한 PDF 텍스트는 분석을 위해 서버와 Gemini로, 음성 스트림은 서버와 Google STT로 전달되므로 “외부 전송이 전혀 없다”고 표현하면 안 된다.
- 자격증명은 브라우저에 노출하지 않고 서버 환경변수·서비스 계정으로 관리한다.

## 6. 평가 실험 설계

### 6.1 최소 실행 가능한 평가 범위

- 서로 다른 3개 분야의 텍스트 PDF를 2개씩, 총 6개 준비한다.
- PDF별로 사람이 정답 전문용어 목록과 첫 등장 페이지를 만든다.
- 분야별 20문장 이상, 전체 60~120문장의 기준 대본과 동일한 녹음 음원을 만든다.
- 같은 음원을 **기본 STT**와 **PDF PhraseSet 적용 STT**에 각각 입력한다.
- 모든 실험의 모델, 언어, 음원, 네트워크 조건을 동일하게 유지한다.

### 6.2 용어집 평가

- **용어 정밀도(Precision)** = 정답 용어인 추출 항목 수 / 전체 추출 항목 수
- **용어 재현율(Recall)** = 추출된 정답 용어 수 / 사람이 만든 전체 정답 용어 수
- **페이지 연결 정확도** = 첫 등장 페이지가 맞은 용어 수 / 평가 용어 수
- **설명 적절성** = 전공자 2명 이상이 정확성·이해 용이성을 각각 5점 척도로 독립 평가
- 비교 조건: Gemini 후보 그대로 vs PDF 원문 재검증 후. 이 비교로 검증 단계의 효과를 보여준다.

현재 API는 최종 용어집만 반환하므로 이 비교를 하려면 실험용 환경에서 원시 후보와 제거 사유를 별도 기록해야 한다. 개인정보가 포함될 수 있는 PDF 본문은 평가 로그에 그대로 남기지 않는다.

### 6.3 음성인식 평가

- **CER(Character Error Rate)**: 한국어 띄어쓰기 변동을 고려한 전체 문자 오류율
- **WER(Word Error Rate)**: 삽입·삭제·대치 오류를 포함한 단어 오류율
- **전문용어 정확도** = 정확히 인식된 목표 전문용어 출현 수 / 전체 목표 전문용어 출현 수
- **전문용어 Recall 또는 Entity WER**를 함께 제시해 전체 문장은 비슷해도 핵심 용어가 개선되는지 확인한다.
- 결과 표에는 기본 STT, PhraseSet 적용 STT, 절대 차이, 상대 개선율을 제시한다.

PhraseSet 때문에 말하지 않은 용어가 잘못 삽입되는 부작용도 따로 센다. 전체 WER이 좋아져도 전문용어가 나빠지거나, 반대 상황이 생길 수 있으므로 두 지표를 함께 해석한다.

### 6.4 실시간 성능 평가

현재 코드에는 신뢰 가능한 발화 시작 시각과 이벤트 시각을 함께 기록하는 계측이 없다. 다음 계측을 추가한 뒤 측정한다.

- 오디오 청크 전송 시각 → 첫 interim 도착 시각
- 문장 종료 시각 → final 도착 시각
- 중앙값, 평균, P95 지연
- 1분·10분·30분 세션의 연결 유지 여부와 오류 횟수

### 6.5 사용자 평가

가능하면 16~24명의 대학생을 대상으로 동일 참가자가 두 조건을 모두 경험하는 within-subject 설계를 사용한다.

- 조건 A: 일반 실시간 자막만 제공
- 조건 B: 자막 + 용어 강조 + 쉬운 설명 + 관련 PDF 페이지 제공
- 강연 순서 효과를 줄이기 위해 두 강연과 조건 순서를 교차 배정한다.
- 사전 지식 3~5문항, 강연 후 이해도 5~8문항, 용어 정의 회상, 과제 완료 시간, SUS 사용성, 주관적 인지부하를 측정한다.
- 자동으로 맥락 카드가 바뀌는 것이 오히려 주의를 분산시키는지 별도 문항과 관찰로 확인한다.

확장 자막이 항상 학습 성과를 높인다고 가정하면 안 된다. 선행 연구에서는 사용자가 확장 정보를 충분히 보지 않아 표준 자막과 이해도 차이가 나타나지 않은 사례도 있다. 따라서 카드 노출 여부나 실제 열람 행동을 함께 측정하는 것이 중요하다.

### 6.6 윤리와 데이터 처리

- 참가자 동의, 녹음 범위, 익명화, 보관 기간을 사전에 고지한다.
- 실제 수업 녹음 대신 동의받은 실험용 대본·음원을 우선 사용한다.
- 외부 AI/API로 전송되는 데이터 항목과 제공자를 명시한다.
- 학과 또는 학교 규정상 연구윤리 심의 대상인지 지도교수에게 확인한다.

## 7. 결과를 쓸 때 필요한 표와 그림

### 논문용 필수 그림

1. **전체 구조도**: 사전 PDF 분석 경로와 실시간 음성 경로를 색으로 구분
2. **용어 검증 흐름도**: Gemini 후보 → 원문 존재 확인 → 정규화·중복 제거 → 50개 제한
3. **화면 구성도**: 자막, 용어 카드, 관련 페이지의 연결 관계
4. **데이터 생명주기**: 브라우저, 서버, Gemini, Google STT 사이 전송과 비저장 범위

### 논문용 필수 표·그래프

1. 데이터셋 구성과 분야별 목표 용어 수
2. 용어 추출 Precision/Recall 및 페이지 정확도
3. 기본 STT와 PhraseSet 적용 STT의 CER/WER/전문용어 정확도
4. 평균·중앙값·P95 지연
5. 조건별 이해도·사용성·인지부하 결과
6. 대표 성공 사례와 실패 사례 3~5개

## 8. 발표 자료 흐름

아래는 **8분 발표 + 2분 데모**를 기준으로 한 11장 구성이다. 시간이 다르면 장수보다 메시지 밀도를 조정한다.

| 장 | 시간 | 제목과 핵심 메시지 | 화면·자료 |
|---|---:|---|---|
| 1 | 0:20 | **자막을 넘어, 맥락까지** | 제품명과 한 문장 가치 제안 |
| 2 | 0:45 | **전문용어 하나를 틀리면 자막도, 이해도도 무너진다** | 일반 자막의 오인식·미이해 상황 한 장면 |
| 3 | 0:40 | **정답 후보는 이미 강연 PDF 안에 있다** | PDF의 용어가 STT와 설명으로 갈라지는 핵심 인사이트 |
| 4 | 0:55 | **사용자 경험: 업로드에서 맥락 자막까지** | 업로드 → 분석 → 강연 → 결과 4단계 |
| 5 | 1:00 | **핵심 1: LLM을 믿는 대신 원문으로 검증한다** | 후보와 검증 후 용어집 비교 |
| 6 | 0:55 | **핵심 2: 하나의 용어집을 두 번 쓴다** | PhraseSet과 설명 카드의 이중 활용 구조 |
| 7 | 0:50 | **실시간으로 연결되는 자막·설명·자료** | 16 kHz PCM → WebSocket → Chirp 3 → UI 구조 |
| 8 | 0:45 | **접근성과 개인정보를 기능으로 설계했다** | 큰 글씨·고대비·전체화면, 데이터 생명주기 |
| 9 | 0:55 | **무엇을 검증할 것인가** | RQ와 A/B 실험 조건, 핵심 지표 |
| 10 | 0:55 | **결과와 한계** | 실제 측정 그래프. 미측정이면 구현 검증과 후속 실험을 분리 |
| 11 | 0:20 | **강연의 말을 보여주는 자막에서, 이해를 돕는 자막으로** | 최종 가치와 확장 방향 |
| 데모 | 2:00 | PDF 분석 결과 → RAG 발화 → 용어 강조·설명·페이지 전환 → 결과 화면 | 실패 위험을 줄이기 위해 내장 데모를 기본으로 준비 |

### 발표에서 기술 스택을 설명하는 방식

React, Vite, Express 같은 목록을 한 장 가득 보여주지 않는다. 기술은 선택 이유와 함께 구조도 안에서 짧게 언급한다.

- PDF.js: 별도 OCR 서버 없이 브라우저에서 텍스트 PDF를 페이지별 추출
- Gemini: 전문용어 후보와 비전공자용 설명을 구조화 JSON으로 생성
- Node.js/Express/Zod: 후보와 실시간 입력을 서버에서 다시 검증
- Google STT V2 Chirp 3: 한국어 실시간 인식과 PhraseSet 기반 적응
- WebSocket: 오디오 업로드와 임시·확정 자막 이벤트 스트리밍
- React: 분석·강연·결과 상태와 접근성 UI 관리

### 데모 멘트의 권장 순서

1. “이 PDF에는 RAG, LLM 같은 강연 특화 용어가 들어 있습니다.”
2. “AI가 후보를 만들지만 PDF에 실제로 없는 표기는 서버가 제거합니다.”
3. “남은 용어를 Google STT 힌트와 청중용 용어 카드에 동시에 사용합니다.”
4. 데모 자막에서 `RAG`가 등장할 때 강조, 쉬운 설명, 3페이지 연결을 보여준다.
5. “현재 결과 화면은 연결된 용어를 보여주는 것이며, 인식률 개선 수치는 정답 대본을 고정한 동일 음원 비교 후 보고합니다.”

## 9. 과장하면 안 되는 현재 상태

- 실제 자격증명으로 PhraseSet 적용 전후 연결 파일럿은 완료했지만, 정답 대본과 실제 발화 후보가 달라 전문용어 인식률로 해석할 수 없다.
- Gemini 3.6 Flash 실제 호출과 한국어 마이크 Chirp 3 스트리밍은 자격증명 연결 후 추가 검증이 필요하다.
- 현재 `easyExplanation`은 용어의 쉬운 정의에 가깝고, 발화 문장 전체를 해석한 “왜 지금 이 용어가 나왔는가” 설명은 아니다.
- 결과 화면의 맥락 연결률은 정확도, 이해도, 인식 개선율이 아니다.
- PDF 원본과 음성을 애플리케이션이 저장하지 않는 것과, 외부 API로 데이터가 전송되지 않는 것은 서로 다른 주장이다.
- 스캔 PDF, 화자 분리, 번역, 장시간 STT 자동 재연결은 현재 범위 밖이다.

## 10. 실제 작성 순서

1. Google 자격증명을 연결하고 실제 end-to-end 경로를 먼저 검증한다.
2. 평가 PDF, 정답 용어집, 기준 대본, 동일 음원을 만든다.
3. PhraseSet 적용 전후 인식률과 실패 사례를 수집한다.
4. 필요하면 지연 계측을 구현하고 반복 측정한다.
5. 사용자 평가가 가능하면 동의·설계를 확정한 뒤 실행한다.
6. 결과 표와 그래프를 먼저 완성한다.
7. 논문의 4장 구현, 6장 평가 방법, 7장 결과를 먼저 쓴다.
8. 그 근거에 맞춰 서론, 관련 연구, 논의, 결론을 쓴다.
9. 논문 그림을 발표용으로 단순화하고 데모를 연결한다.
10. 발표 직전에는 실시간 API 경로와 내장 데모 경로를 둘 다 준비한다.

관련 연구 절에서는 선행 연구의 수치를 이 프로젝트의 예상 성능처럼 옮기지 않는다. 각 연구가 보여준 것은 “왜 이 연구문제가 타당한가”에 사용하고, 본 시스템의 효과는 자체 실험 결과로만 주장한다.
